// Infrastructure réseau — Semaine intensive inter-filière

ClassCord

📅 Semaine intensive — Jan 2025

Documentation technique

Semaine intensive inter-filière à IRIS Mediaschool Nice. Mission SISR : déployer, sécuriser et administrer un serveur de tchat TCP/IP Python multi-clients accessible aux étudiants SLAM depuis le réseau pédagogique interne. Les étudiants SLAM ont développé les clients Java ; notre rôle SISR était exclusivement côté infrastructure serveur.

Architecture réseau : Le serveur Python tourne sur une VM Linux Debian (192.168.x.x) hébergée sur le poste hôte SISR (10.0.108.42). Une règle NAT est configurée sur l'hôte pour que les connexions entrantes sur 10.0.108.42:12345 soient redirigées vers la VM. Les clients SLAM (ex : 10.0.108.34) se connectent à l'IP de l'hôte physique sans connaissance de la VM.

Stack technique : Python 3 (sockets TCP, port 12345, multi-threads) — Docker & docker-compose (image portable reproductible) — systemd (service classcord.service, user système dédié, Restart=on-failure) — SQLite (persistance utilisateurs + messages horodatés) — fail2ban (filtre connexions anormales) — UFW/iptables (whitelist réseau pédagogique) — rsyslog + logrotate (logs applicatifs centralisés).

Organisation 5 jours : J1 : déploiement local + tests 2 clients · J2 : exposition réseau (NAT), Docker, systemd, doc_connexion.md · J3 : sécurité active (fail2ban, UFW, sauvegardes cron horaires) · J4 : évolutions fonctionnelles (canaux JSON #général/#dev/#admin, SQLite, messages système) · J5 : démo croisée SISR/SLAM, finalisation dépôt GitHub, fiche RP.

Compétences BTS SIO SISR mobilisées

Déploiement et administration d'un service réseau Sécurisation d'un service (fail2ban, UFW, logs) Virtualisation et containerisation (Docker) Automatisation système (systemd, cron) Travailler en mode projet inter-filière Mettre à disposition des utilisateurs un service informatique Gestion des incidents et demandes de service (ITIL)

Livrables

  • Serveur Python TCP multi-clients opérationnel (port 12345, service systemd actif)
  • Image Docker déployable (docker-compose up)
  • Service systemd classcord.service avec redémarrage automatique
  • Sécurisation : fail2ban configuré, UFW whitelist, logs rsyslog centralisés
  • Sauvegarde automatique SQLite via cron (toutes les heures)
  • Documentation d'accès client (doc_connexion.md — IP, port, schéma NAT)
  • Dépôt GitHub avec commits quotidiens et README complet

Critères d'évaluation

2+ clients SLAM connectés simultanément depuis le réseau pédagogique
Service systemd actif et redémarrage automatique validé
fail2ban opérationnel (tentatives bloquées journalisées)
Image Docker fonctionnelle (docker-compose up)
Sauvegarde SQLite automatique (cron horaire)
README et doc_connexion.md accessibles et complets

Modalités de clôture

Démonstration J5 avec au moins 2 clients Java SLAM connectés simultanément. Présentation de la sécurité (fail2ban actif, logs, UFW), des mécanismes de disponibilité (systemd restart automatique), et des livrables (image Docker, dépôt GitHub, fiche RP). Livraison quotidienne validée (J1→J5) par commits Git datés. Approche ITIL : le service classcord.service constitue un catalogue de service interne livré avec sa documentation d'accès, ses niveaux de disponibilité (RTO < 2 min) et son journal d'incidents (rsyslog).

Gestion des risques

Risque identifiéProbabilitéImpactMesure de mitigation
Incompatibilité protocole client Java / serveur Python Élevée Élevé Tests croisés quotidiens dès J1 avec le client de référence du formateur
Indisponibilité de la redirection NAT (réseau pédagogique) Moyenne Élevé Documentation d'un port de secours + coordination formateur J2 pour validation NAT
Crash serveur Python (exception non gérée, déconnexion brutale client) Moyenne Élevé systemd Restart=on-failure + journalisation complète des exceptions Python
Attaque brute-force ou connexions malveillantes sur port 12345 Faible Moyen fail2ban (filtre connexions anormales) + UFW whitelist sur le sous-réseau pédagogique
